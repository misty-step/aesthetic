# aesthetic — agent contract

One CSS file is the product. `aesthetic.css` ships to production
consumers who pin git tags; everything else in this repo exists to
develop, prove, and publish that file.

## The law

The canonical statement lives in the header of `aesthetic.css` and in
`tokens.json` (`law`). Never violate it in any surface this repo
renders: one font size (13px chrome register is the one exception),
nine registers from three inks × three weights, the accent is the
consumer's to steer (identity comes from ink, hairlines, type, and
motion — color earns its place), status rides the glyph, viewport
screens that never scroll, motion as feedback only (resolves once,
persists), buttons are not links. The steering doctrine — invariants
vs dials — lives in `docs/ADOPTING.md`.

## Repo shape

- `aesthetic.css` + `tokens.json` + `recipes/` — the package (npm
  `files` allowlist). `tokens.json` carries the contrast table —
  recompute it whenever a color token changes.
- `recipes/` — the canonical behavior layer: one dependency-free
  snippet per behavior, combined into `recipes/recipes.js` by
  `npm run build:recipes` (CI checks the combination is fresh).
- `DESIGN.md` — the identity in prose, for agents generating anything
  visual (views, components, images). Read it before visual work;
  `docs/IMAGES.md` is the extended image-language canon;
  `docs/ADOPTING.md` is the consumer-facing adoption guide with the
  worked steering blocks.
- `site/` — the public site: one simple gallery of the primitives
  (plus the generated tokens page), built only with the
  system itself: zero build step, zero framework. It is the ONLY
  consumer that rides HEAD; `site/aesthetic.css` and
  `site/recipes.js` are symlinks to the root artifacts. View-source
  is documentation — keep markup canonical.
  - `site/tokens.html` is a **generated file** (`npm run build:tokens`
    from `scripts/build-tokens.mjs`) — `npm run check` fails with
    "out of date" if it drifts from what the script would produce.
    Edit the nav/template inside `build-tokens.mjs`, never the
    generated HTML directly, then regenerate.
  - `site/law.html` is partially generated (`build-law.mjs` owns an
    embedded section, checked by `npm run check`) but its shell/nav is
    hand-authored — safe to hand-edit the shell; run `npm run check`
    before assuming any edit there is safe.
- `site/r/` — the registry: static JSON regenerated by
  `npm run build:registry` (never edit by hand). It has a shadcn
  root index (`registry.json`), whole-kit items (`aesthetic.json`,
  `recipes.json`), a generated shared base item
  (`aesthetic-base.json`), and one per-primitive item at
  `<route>.json` matching `site/r/primitives.json`. Primitive items
  declare an absolute `registryDependencies` URL for
  `aesthetic-base.json`, embed
  only their CSS selector/token slice plus recipe singles, and carry
  the package version in `meta.version`.
- `prototypes/` — design experiments (LAB convention). Local only:
  committed for history, NEVER deployed; the Pages workflow stages
  `site/` exclusively. Prototype files never graduate by copy — the
  locked direction gets rebuilt properly in `site/`.
- Product work is tracked in the deployed Powder board, never in this repository.

## Gates

Run before any commit that touches CSS/HTML/JS:

```sh
npm run ci
```

CI (`.github/workflows/ci.yml`) runs the same command after installing
Playwright's Chromium browser. It includes the Playwright law gates
(`tests/law.spec.ts` — font sizes, radius 0, no page
scroll, console cleanliness on every stable page, both modes) on
every push. Do not loosen `.stylelintrc.json` or the law spec to get
green; the disabled rules there are deliberate house-style
calibrations, documented by their grouping.

## Release flow

1. Land changes on master (site rides HEAD, so the deploy follows).
2. `node scripts/release.mjs X.Y.Z` — bumps `package.json`, the
   `aesthetic.css` header, README/site/ADOPTING pin references,
   `tokens.json`, and regenerates the registry; then commits and tags
   `vX.Y.Z`.
3. Push with tags. Consumers pin tags and upgrade deliberately —
   never bump them implicitly; adoption work does that
   per-repo with evidence.
4. Pages deploys `site/` automatically on push to master
   (`.github/workflows/pages.yml`).

## Verification

The site is the proof surface: serve the repo root
(`python3 -m http.server`) and walk `site/` in a browser — both modes,
the specimen grid, a few plate routes (send moment, toast, dialog),
and the tokens page. Tests pass ≠ verified; render it.
